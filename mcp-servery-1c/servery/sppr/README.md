# СППР

Сервер ищет и читает фрагменты конфигурации **1С:Система проектирования прикладных решений** 2.0.11.11:
метаданные, модули, формы и встроенная справка самой СППР. Отдельный снимок двух
справочников позволяет получить проект и карточки его технических проектов с их статусами.
С 23.11.2026 сервер читает и **модель прикладного решения** из базы СППР: функции системы,
подсистемы, объекты метаданных, справку, целевые задачи, идеи, функции механизмов и статусы
встраивания — у неё свой корпус Markdown и свой индекс. Сервер читает все снимки с диска.

С 05.11.2026 СППР входит в основной состав MCP. Образ на Docker Hub не опубликован,
лицензионного ключа нет, порта нет. Установщик Docker-поставки контейнер не запускает
и в `mcp.json` запись не добавляет. Инструкция дистрибутива — `servers/10_SPPR.md`.

## Как запущен

Процесс со транспортом stdio. Его поднимает MCP-клиент на машине, где развёрнут
каталог исходников `pre-alpha/MCP_SPPR`. Отдельного URL `/mcp` нет.

Индекс — SQLite FTS5, файл `data/sppr.sqlite3` в каталоге проекта. Путь можно
задать переменной `SPPR_INDEX_DB`.

Карточки берутся из `data/projects.json` (путь переопределяется переменной `SPPR_PROJECTS_FILE`).
Для обновления запустите из каталога сервера `scripts\export_projects.ps1 -Base <каталог файловой базы>`
в Windows PowerShell той же разрядности, что и зарегистрированный COM-коннектор 1С (`V83.COMConnector`).
Пользователь базы задаётся параметром `-User`, по умолчанию «Администратор»; пароль при
необходимости — параметром `-Password` (в снимок и вывод не попадает).
Скрипт читает справочники «Проекты» и «Технические проекты» через COM, освобождает COM-объекты
и заменяет файл после успешной выгрузки. Сервер перечитывает снимок при каждом запросе.

Тот же скрипт выгружает модель: записи справочников — в `data/model.jsonl`, затем корпус
`data/model/{uuid-проекта}/{тип}/{uuid}.md` (шапка YAML и текст Markdown, справка переводится
из HTML) и индекс `data/model.sqlite3`; оба заменяют прежние только целиком. Пути
переопределяются переменными `SPPR_MODEL_DIR` и `SPPR_MODEL_DB`. `-SkipModel` обновляет только
карточки. Пароли и имена пользователей хранилища, каталоги баз, учётные записи и почта не
выбираются. Расширения в базе СППР и инкрементальной выгрузки пока нет: модель выгружается
целиком (база на 39 тысяч объектов — около трёх минут).

## Инструменты

Все инструменты помечены аннотацией `readOnlyHint: true` (`openWorldHint: false`):

| Инструмент | Что делает |
|---|---|
| `sppr_index_status` | Готовность индекса, число документов, фрагментов, разбивка по категориям метаданных и статистика снимка карточек (включая счётчики статусов) |
| `sppr_search` | Полнотекстовый поиск (сохраняет CamelCase-идентификаторы 1С, приоритет совпадениям всех слов). Параметры: `query`, `limit`, `source_prefix` |
| `sppr_explain` | Фрагменты для объяснения темы |
| `sppr_traceability` | Кандидаты связей требования: сгруппированные по категориям фрагменты конфигурации (`configuration_hits`, `by_category`) и совпадающие карточки проектов / технических проектов (`project_cards`) |
| `sppr_sources` | Постраничный список проиндексированных источников корпуса с числом фрагментов (`source_prefix`, `query`, `offset`, `limit`) |
| `sppr_read_source` | Постраничное чтение упорядоченных фрагментов конкретного источника из индекса SQLite (`source`, `offset`, `limit`) |
| `sppr_projects` | Записи справочника «Проекты» с кодом, наименованием, UUID и числом технических проектов; фильтр `query` |
| `sppr_technical_projects` | Технические проекты с фильтрами `project_uuid`, `status` (полное русское название), `section`, `version`, `query` и сводкой `status_counts` |
| `sppr_object` | Карточка по `uuid` или уникальному `code`. Для технического проекта возвращается `project_name`, для проекта — `technical_projects_summary`, для обоих — `model` из модели проекта. Любой объект модели — по `uuid` либо `type` и коду: шапка и текст Markdown, у функции системы — `связанная_реализация` (вывод по связям, `inferred: true`) |
| `sppr_model_search` | Полнотекстовый поиск по модели проекта, отдельно от конфигурации СППР. Параметры: `query`, `project`, `type` (`technical_project`, `function`, `subsystem`, `metadata`, `help`, `target_task`, `idea`, `mechanism`, `section`), `limit`, `offset` |
| `sppr_functions` | Функции системы: полный код, наименование, подсистема, родитель; фильтры `subsystem`, `code_prefix`, `parent`, `query` |
| `sppr_subsystems` | Подсистемы: иерархия, полный код, присутствие в основном хранилище, число объектов в составе |
| `sppr_metadata` | Объекты метаданных модели: фильтры `kind`, `in_storage`, `subsystem` (состав, с `include_children` — и подчинённых подсистем), `query` |
| `sppr_target_tasks` | Целевые задачи со статусами |
| `sppr_mechanisms` | Функции механизмов и строки регистра статусов встраивания |
| `sppr_gap` | Независимые счётчики «сделано / не сделано»: статусы технических проектов, целевых задач, идей, встраивания; объекты метаданных и подсистемы в хранилище и вне его. `detail=true` — страницы «надо встроить» и объектов вне хранилища |
| `sppr_links` | Связи объекта в обе стороны, записанные выгрузкой (не угаданные поиском) |

Списки принимают `offset` и `limit` (по умолчанию 200, максимум 500).
Ответ содержит `total`, `truncated`, дату выгрузки и имя базы. В `sppr_index_status`
поле `ready` относится к индексу конфигурации, `project_snapshot.ready` — к карточкам,
`model.ready` — к модели проекта (с числом объектов по типам и временем выгрузки).

Каждый фрагмент содержит источник, заголовок, раздел, текст и SHA-256.
`sppr_traceability` возвращает кандидатов из текста конфигурации и снимка карточек, а не гарантированный граф связей базы.

Ресурсы MCP: `sppr://about` — краткое описание сервера, `sppr://threat-model` — модель угроз.
