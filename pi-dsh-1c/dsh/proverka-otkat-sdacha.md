# Проверка, откат и сдача в DSH

## Локальная проверка

«Проверь локальным BSL LS модуль <путь>» вызывает `onec_bsl_query`. Java и BSL Language Server входят в архив каждой платформы. Через MCP доступны syntaxcheck, проверка 1С:Напарника и `verify_xml`, если соответствующий сервер жив.

`/features rejectInvalidBsl on` отклоняет заведомо неверный BSL до записи. По умолчанию выключено. `/features completionGate on` не даёт закрыть шаг, пока проверка текущих файлов не прошла. Проверка завершения следит только за файлами `.bsl` и `.xml` вне `openspec/` и `docs/`: правки остальных файлов ход не останавливают. Три одинаковые ошибки останавливают повтор отдельно от этого ворот.

Если изменения сделаны командами оболочки и не проверены автоматически, DSH показывает вам отдельную строку: «задайте `/features verifyCommand <команда>`». В переписку с моделью это замечание не попадает, в том числе в чатах, начатых до этого исправления.

`/features manualCheck on` после неудачи готовит 3–7 шагов ручной проверки. `/manual-check Работает` засчитывается только для текущих файлов после неуспешной автоматической проверки. Новая правка требует пройти шаги заново. Истечение времени успехом не считается.

`/features reviewStrictness` принимает `low`, `normal` или `strict`. Дешёвая модель фильтра замечаний задаётся отдельно от основной. Если она не подключена, карточки остаются с явной пометкой, что фильтр не выполнен.

`/features platformVersion` и `bspDatabase` ограничивают справку. Пример базы БСП: `3111.db`. Сравнение версий БСП вызывает две базы. У справки платформы нет отдельного корпуса на каждую версию.

`/deslop` убирает артефакты генерации из BSL. Сначала список, `apply` — по запросу.

Кнопка **«В чат»** добавляет путь открытого модуля или элемента формы в черновик. Вопрос дописываете вы.

## Формы, макеты и EDT

- **Обработчик элемента формы.** «Файлы → Метаданные 1С → Визуальный предпросмотр → Элементы формы и обработчики» → «Открыть обработчик» открывает процедуру модуля формы.
- **Параметр макета.** У ячейки макета есть «Параметр макета» и «Добавить параметр в чат»: в черновик попадают путь к `Template.xml`, имя параметра и адрес ячейки вида `R7C4`. У объединённой ячейки берётся левый верхний угол.
- **Сравнение формы.** «Сравнить форму с HEAD» показывает отличия рабочего `Ext/Form.xml` от последнего коммита Git.
- **Замечания к строкам `.mdo`.** Замечание ревью к строке файла EDT открывается кнопкой «Открыть замечание». После изменения файла замечание помечается устаревшим.

Предпросмотр форм и макетов работает на XML выгрузки Конфигуратора. Большая выгрузка EDT открывается в дереве метаданных упрощённым деревом по `Configuration.mdo`, подробности объекта подгружаются при раскрытии.

## Загрузка в базу

В **1С Full** и доступе BUILD агент сам загружает сделанное изменение в выбранную базу штатным `onec_deploy` и проверяет его. После ошибки он исправляет код и повторяет загрузку. Вводить `/deploy-and-test`, нажимать кнопку и подтверждать каждый шаг для этого не нужно. В ASK и PLAN загрузка не запускается. При конфликте в Конфигураторе решение о перезаписи остаётся за вами.

`/update1cbase` предлагает план `onec_deploy`. В BUILD запуск из чата идёт без отдельного окна подтверждения бандла. Окно деплоя можно использовать и вручную: кнопка «Загрузить» по-прежнему спрашивает подтверждение. После успешной загрузки стартует переиндексация code MCP и привязанного graph. Пока она не подтверждена, старый поиск закрыт.

`/deploy-and-test` оставлена для ручного запуска загрузки с проверкой интерфейса.

Снимок `.dt` загружает навык `1c-metadata-manage` (`db-load-dt`), затем `/update1cbase`.

Назначение базы (`test`, `dev`, `production`) в операции не вмешивается. Не проверяйте доработку на рабочей базе.

## Откат файлов

Автоматические снимки выключены, в том числе в Git-проектах. Старые настройки автоснимков в Desktop это не включают.

| Команда | Что делает |
|---|---|
| `/checkpoint` | Ручная точка |
| `/checkpoint list` | Список без обхода проекта |
| `/rewind` | Список точек |
| `/rewind preview latest` | Что изменится |
| `/rewind workspace latest` | Вернуть сохранённые файлы после подтверждения |

Без Git снимок копирует проект целиком и на большой выгрузке может идти долго. Git-снимок покрывает только отслеживаемые файлы и тоже не обещает мгновенность. Защитный снимок перед откатом может быть таким же долгим.

Если точки до правки нет, эту правку откат не гарантирует. Информационная база в снимок не входит.

## Сдача

1. Закройте задачи: `/openspec1c task … done <revision> <evidence>`.
2. `/openspec1c validate <change>`.
3. Описание поставки по маршруту правил: `/rules1c route поставка`.
4. `/build-release` собирает `.cf` или `.cfe` в `build/`. Это бинарник поставки, не копия XML, и базу само по себе не обновляет.
5. Загрузка в тестовую базу в BUILD, без отдельного окна подтверждения бандла.

`/merge1c` готовит план нетипового обновления. Применение — отдельное подтверждение. Объекты на поддержке поставщика переносятся в расширение, когда support-guard распознал поддержку по выгрузке.

## Журнал и поддержка

`/journal1c` читает журнал регистрации, не технический журнал. `/support` собирает черновик по классу `harness`, `mcp`, `rules` или `other`. `/support send` отправляет его, если заданы `SUPPORT_KEY` и `SUPPORT_EMAIL`. Ключ в интерфейсе виден только как «настроен». `/supportstatus` показывает ответы.

`/receipt` перечисляет действия, которые расширение реально наблюдало, и решения подтверждений. Неизвестное состояние не считается вашим разрешением. Секреты в URL скрываются. Разговоры до появления расширения задним числом не пересчитываются.

`/receipt` и `/receipt html` показывают и прикладные сценарии из свежего отчёта JUnit. Команда проверки задаётся `/features verifyCommand <команда>`, путь к отчёту — `/features scenarioReport <путь>`. Это команды пресета 1С Full.
