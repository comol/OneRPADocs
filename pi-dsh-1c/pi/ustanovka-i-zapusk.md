# Установка и запуск Pi

Распакуйте весь ZIP в отдельную папку. Из этой папки один раз выполните установщик.

```powershell
.\Pi-1C.exe --install
```

Если контейнеры MCP ещё не запущены:

```powershell
.\Pi-1C.exe --install -SkipMcpProbe
```

Статическая проверка состава восьми MCP выполняется и с `-SkipMcpProbe`. Live-probe и пробный запуск сессии в этом случае откладываются.

## Что делает установщик

1. Проверяет Node.js.
2. Сверяет `node_modules` и `package-lock.json` с манифестом SHA-256.
3. Восстанавливает зависимости только если runtime отсутствует или указан `-ForceRestore`, и снова сверяет манифест.
4. Проверяет целостность runtime. Клиентские developer-тесты при этом не запускаются.
5. Проверяет закреплённые `rg.exe` и `fd.exe`: хеш, архитектуру AMD64 и реальный `--version`.
6. Проверяет состав поставки, происхождение файлов, allowlist навыков и скриптов, ровно восемь включённых MCP и отсутствие секретов в зависимостях и бинарниках.
7. Без `-SkipMcpProbe` опрашивает восемь серверов: identity, каталог и схемы.
8. Запускает Pi в изолированном RPC-режиме и проверяет инструменты, 71 хешированный скрипт, навыки и 40 промптов. Зависшая попытка снимается и повторяется один раз.
9. Повторяет полную проверку после smoke.
10. Регистрирует пользовательскую команду `startpi1c`.

Установщик ничего не удаляет. Если внутри дистрибутива найдены чужие runtime-файлы, установка останавливается: разбирайте вручную, данные не стираются.

| Параметр | Назначение |
|---|---|
| `-ForceRestore` | Восстановить `node_modules` из lock-файла и снова сверить манифест |
| `-SkipMcpProbe` | Не делать live MCP probe и RPC smoke |
| `-SkipCommandRegistration` | Не регистрировать `startpi1c` |
| `-CommandDirectory <путь>` | Куда положить shim вместо `Programs\Pi1C\bin` в профиле пользователя |
| `-SkipUserPathUpdate` | Создать shim, но не менять User PATH |

## Первый вход

Запустите `Pi-1C.exe` без аргументов. В списке создайте проект («Новый проект») или добавьте существующую папку. Пароли вводите в мастере `Pi-1C.exe --setup`, не в чате.

В терминале появится карточка «Готовность». Дальше:

1. `/setup` — пять полей `.dev.env`: путь платформы, версия, EDT, вид и путь базы, префикс. Существующий файл мастер не перезаписывает.
2. `/login` и `/model` — вход и модель. Cursor: `/cursor-login`, затем `/cursor-refresh-models` и `/model`. Claude: `/claude-login`, только подписка Max через CLI `claude`.
3. `/openspec init` — каталог `openspec/`, когда вы ведёте изменения через change.
4. `/mcp1c` — семь профильных серверов и QA. Строка статуса отделяет «MCP 1С: 7/7» от общего счётчика проверок проекта.

Навигатор команд: `/commands1c` или Ctrl+Alt+H. Памятка маршрута без хода модели: `/process1c`. Меню настроек: `/settings1c`. Гайд по окну: **Помощь → Гайд по интерфейсу** или F1, в терминале — `/help1c`.

Обновление самой поставки: `/app-update` спрашивает загрузку и отдельно — установку с перезапуском. `/bundle-updates` управляет фоновой проверкой раз в сутки. Правила 1С и образы MCP установщик сам из сети не подменяет: `/checkupdates` и `/updaterules` объясняют, где лежит источник и кто выполняет импорт.

## Если установщик или старт спорит с MCP

Молчащие серверы — это degraded, а не «сборка сломана». Красная ошибка конфигурации означает другое: повреждённый ZIP, чужие файлы в `agent/` или несовпадение манифеста. Распакуйте архив заново и повторите `--install`.

Диагностика:

```powershell
.\Pi-1C.exe --doctor -WorkingDirectory <папка проекта>
```

В сессии: `/preflight1c`, `/mcp1c`, `/status1c`, `/installtools`, `/doctor`. Отчёт для поддержки без секретов — `Pi-1C.exe --support-report`. Текст обращения готовит `/support`; отправляете его вы.
